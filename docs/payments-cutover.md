# Payment and host remediation cutover

This release replaces new bid and subscription payments with Money Dev Kit. It includes the work from PR #111 and supersedes that PR as the complete application change. The original [audit](audits/2026-09-11-app-status.md) describes main at `d72c0e9`; its findings are historical, not assertions about this branch.

**Production hosting:** `https://pleb.fm` currently returns Netlify responses and resolves to Netlify. The repository's Netlify project is `pleb-fm`; the separate linked Vercel project does not own that domain. Configure and verify the live Netlify project before merging to its production branch. Do not treat Vercel environment changes or a successful Vercel preview as production setup. No DNS migration is part of this release.

## Before deployment

1. Back up MongoDB and the MDK mnemonic. Use an Atlas cluster or MongoDB 6+ replica set with transactions. Keep production credentials out of preview environments on **both hosting providers**. Vercel and local isolation are complete; Netlify configuration remains unverified until account access is available. Use a database user scoped to the staging database, not the existing broad Atlas role with a different database name.
2. Set the variables in `.env.sample` in the intended environment. Configure an app-scoped MDK key, mnemonic, two **monthly USD products** (Basic 500 cents, Pro 2,000 cents), and their IDs. Do not enable `MDK_PREVIEW` or `NEXT_PUBLIC_MDK_PREVIEW` for real bids or subscriptions; sandbox money never earns real credit.
3. Register the MDK node endpoint `/api/mdk` and business webhook `/api/webhooks/mdk`. Use the business endpoint's Standard Webhooks signing secret as `MDK_WEBHOOK_SECRET`. Subscribe to `checkout.completed` and subscription lifecycle events. These are different endpoints and different secrets. Keep the legacy Stripe endpoint `/api/billing/webhook` configured and signed until existing subscriptions finish.
4. Remove `NODE_TLS_REJECT_UNAUTHORIZED=0` wherever it was configured. Revoke/re-authorize exposed Spotify grants after deploying the response/authorization fix. Old PlebFM auth sessions are invalidated by `authVersion: 2`; that does **not** revoke a refresh token already copied by another party. Spotify account owners must remove the app grant and reconnect. No misuse was established by this audit.
5. Run `pnpm preflight --env-file=/private/path/production.env` against the intended environment. It reports configuration presence, database topology, missing indexes and record counts, and inventories Stripe subscriptions when a Stripe key is present. The default mode writes no database data. Use `--database-only` to inspect database readiness independently of provider setup. Use `--database-only --apply-schema` to install required unique indexes and then remove the obsolete refresh-token index. Do this before accepting payments. It does not drop other indexes or erase payment history. An index failure is a release blocker; investigate conflicting data rather than deleting it. The migration has been applied to the database in Vercel Production after a verified restore rehearsal; confirm Netlify uses the same connection. The old application was observed recreating its legacy index after migration. Retire old deployments at cutover, rerun the migration and verify again before accepting new payments; removing it while old code still runs is only temporary.
6. Review the Stripe inventory. `pnpm preflight --import-stripe` imports authoritative subscription state using Stripe metadata or the originating checkout's metadata. Investigate unmapped subscriptions individually. It does not charge, cancel or transfer any subscription. Existing hosts retain their paid period; new checkout creation rejects overlapping subscriptions. Historical receipts before this release need separate verified import if required; the app never fabricates them.
7. Configure Vercel domain automation with a token scoped to this project/team. Domain attachment requires both the PlebFM ownership TXT challenge and Vercel's DNS checks. Free/expired plans cannot use custom domains or custom branding. Never assign an already-owned domain to another host without verifying ownership.
8. On Netlify, `reconcile-schedule` runs every minute and dispatches `reconcile-background`, which calls the existing `/api/jobs/reconcile` endpoint using `CRON_SECRET`. Both functions require the current published production deployment; previews do not dispatch into the production site. The background hop avoids Netlify's [30-second scheduled-function limit](https://docs.netlify.com/build/functions/scheduled-functions/). Next.js is packaged as a streaming function with a [60-second limit](https://docs.netlify.com/build/functions/api/#streaming-responses). Verify a real scheduled invocation after deployment, including background-function logs: a successful dispatch only means the job was queued. If using Vercel, the linked Pro team supports `vercel.json`'s every-minute cron ([Vercel limits](https://vercel.com/docs/cron-jobs/usage-and-pricing)). Monitor non-2xx responses, unresolved creations, webhook delivery failures and payout reservations. The bounded endpoint handles eleven records per invocation with three workers; increase throughput through measured load testing, not an unbounded batch.
9. Do not auto-sweep the MDK wallet below host liabilities. Pro bids credit the **provider-reported net sats**; Free/Basic bid receipts fund the platform. Outbound routing fees are currently paid by the platform, not deducted from host balances. `MDK_PAYOUTS_ENABLED` is an operational gate. Enable it in an isolated test environment for the withdrawal smoke test, then enable production only after the wallet covers host balances and pending withdrawals.

## Required live acceptance

Automated tests use synthetic provider results. A successful build and test suite are not proof that the real wallet, Spotify account, webhook delivery or DNS setup works.

- In an isolated staging app/database, pay a small real bid from an external Lightning wallet. Confirm exactly one order, bid and ledger credit. Close the browser before paying another invoice; verify webhook/cron fulfillment and queue notification. Reopen/retry and replay the webhook; totals must remain unchanged.
- Let an invoice expire. Verify its reservation is released once, the same expired request cannot be paid again, and an explicit retry creates a new intent. Disconnect the provider and retry: a request with an unknown result must keep its original identity.
- Complete a Basic/Pro subscription. Verify provider product/currency/price, paid-period entitlement, receipt download, renewal reminder links and cancellation through period end. Confirm failed/expired renewals remove entitlements after the paid period.
- Withdraw a small earned balance. Confirm the destination amount and terminal provider result. Retry the same withdrawal; there must be one debit/payment. Exercise a confirmed failed payout in staging and verify one refund. Do not manually refund a merely timed-out payout.
- Connect a real Spotify Premium venue account. Verify OAuth refresh, new-user onboarding, empty queue start, adding a paid song, next/playing/played transitions, skip and device reconnection. Catalog and playback requests use different credentials; a Spotify outage must not prevent settlement of a previously created order.
- Attach a test domain you control using the shown TXT/DNS records, verify routing to the correct venue, then remove it. Check Pro branding, plan expiry, analytics, authenticated receipt access and deletion with zero balance/no pending money.

## Recovery and cutover rules

Orders are saved before any provider call. For MDK, the checkout ID is saved before invoice minting. An interrupted mint resumes the stored checkout. Settlement validates the payment hash, currency and exact amount; a Mongo transaction updates the venue account, bid and order together. Provider callbacks and polling may repeat safely. Notifications are retried after transaction commit.

If the **initial create** request loses its response, the order remains `creating`/`uncertain` with no provider reference. The app will not mint a replacement. The cron returns a non-2xx response once such records are older than two minutes. Locate the MDK checkout using the saved `bidOrderId` or `billingRequestKey` metadata, verify its identity and amount in the provider dashboard, then POST JSON to `/api/jobs/reconcile` with `checkoutId` and exactly one of `orderId` or `billingRequestKey`, authenticated with the cron bearer secret. This operator recovery path re-fetches and verifies the provider record before attaching it. The next reconciliation resumes the original checkout. The documented webhook payload does not guarantee a checkout ID, so do not rely on replay alone for this case. If no payable invoice exists, resolve the record only after provider confirmation. Keep a support record for any manual action. Do not clear an uncertain record merely because time passed.

Withdrawals reserve funds transactionally before dispatch. Every provider retry uses the same idempotency key. Confirmed `FAILED` returns the reservation once; `SUCCESS` completes it. Network timeouts and configuration failures leave funds reserved until reconciled. Resolve the provider/configuration issue and retry the saved withdrawal. Never submit it with a fresh idempotency key or manually credit back an unknown outcome.

Old stateless invoice hashes cannot prove their original amount/song/owner and are deliberately rejected by the new public API. Pause old invoice creation, allow its documented expiry window to pass, and inventory payments received around cutover. Reconcile any paid/unfulfilled legacy invoices from provider records with the payer/host individually. Do not infer historical earnings from caller-supplied bid amounts; historical unaudited bids are not imported into the new money ledger. Keep LNbits read credentials while outstanding legacy records are investigated.

Rollback must preserve the ledger and reconciliation endpoints. Do not roll back to the original stateless settlement route or publicly serialize full host records. If MDK is unavailable, stop new checkouts while continuing reconciliation; changing `PAYMENT_PROVIDER` only affects new bids and cannot migrate existing payment identities. Paid subscriptions continue to be read from stored authoritative state until the end of their paid period.

## Local checks

`pnpm db:snapshot --env-file=/private/path/production.env --output=/private/path/new-backup-directory --rehearse-migration` reads all ordinary collections in one snapshot transaction, saves raw BSON plus index metadata outside the repository with private file permissions, verifies a byte-for-byte local restore, and runs the index migration against that disposable copy. It refuses an existing output directory or changed collection/index metadata. It is intended for this small application's data, not cluster users, Atlas settings, continuous backup or point-in-time recovery. Existing backups can be rechecked with `pnpm db:snapshot --verify=/private/path/backup-directory --rehearse-migration`. The CLI accepts no remote restore destination. Keep backups private and arrange encrypted off-machine retention through the database owner.

`pnpm check` runs lint, typecheck, transactional and route tests, and a production build. `pnpm audit --prod --audit-level moderate` must pass. CI runs the same checks on Ubuntu/Node 22, providing the Linux native-dependency build check that a macOS build cannot supply.

CI also runs `npx --yes netlify-cli@27.5.2 build --offline --context deploy-preview` to package the actual production hosting adapter and both scheduling functions. This checks the deployment bundle without deploying it or using production secrets. Netlify account configuration, native module execution on its live Linux runtime and external callbacks still require hosted acceptance.

`pnpm smoke:local` runs the production build with a temporary MongoDB replica set, synthetic host identity, and blank server provider credentials. For entirely isolated browser testing, build first with `NEXT_PUBLIC_PUSHER_APP_KEY= NEXT_PUBLIC_BASE_URL=http://localhost:3100 pnpm build`; public values are baked into browser bundles. The sign-in helper runs only on loopback and is absent from deployed routes. It does not test real OAuth or money movement.
